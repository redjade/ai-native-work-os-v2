# 2주차: 위임·프롬프트 개선과 검증

## 이번 주 목표

AI에게 일을 맡길 때 필요한 정보를 구조화하고, 결과를 관찰해 지시를 한 줄씩 개선하며, 결과가 맞는지 확인한 증거를 남깁니다.

## 핵심 원칙

좋은 결과는 긴 프롬프트보다 명확한 작업 계약에서 나옵니다. 이 과정에서 말하는 프롬프트 엔지니어링은 **정답 문장을 외우는 일**이 아니라, 작업을 작게 정의하고 결과를 보고 다음 지시를 고치는 일입니다.

처음에는 아래 네 칸만 채우면 됩니다.

```text
할 일: 무엇 하나를 할까?
자료: 무엇을 보고 할까?
경계: 무엇을 하지 말아야 할까?
끝: 무엇이 나오면 끝일까?
```

작업이 끝난 뒤에는 다음 한 줄을 덧붙입니다.

```text
불확실하거나 사람이 확인할 항목을 따로 표시해 주세요.
```

필요한 경우에만 목표·맥락·제약·완료 조건·검증을 더 자세히 적습니다.

```text
목표: 무엇을 만들거나 바꿀 것인가?
맥락: 어떤 파일, 자료, 사용자 상황을 알아야 하는가?
제약: 하지 말아야 할 것과 지켜야 할 기준은 무엇인가?
완료 조건: 언제 끝났다고 판단하는가?
검증: 결과가 맞다는 것을 어떻게 확인하는가?
```

## 실습 1: 최소 작업 프롬프트 만들기

30~90분 안에 끝낼 작업 하나를 고르고, 먼저 네 칸으로 지시를 씁니다. 한 번에 프로젝트 전체를 맡기지 않습니다.

```text
할 일: `sources/`의 논문 세 편 초록을 표로 정리해 주세요.
자료: `sources/` 안의 세 파일만 읽어 주세요.
경계: 원문에 없는 주장을 추가하지 말아 주세요.
끝: 연구 대상·방법·주요 결론·파일명·페이지가 있는 표를 만들고, 근거가 불분명한 셀을 따로 표시해 주세요.
```

이 네 칸으로도 모호하면 [작업 지시서 템플릿](../templates/task-brief.md)의 나머지 항목을 채웁니다. 템플릿은 긴 프롬프트를 강요하는 양식이 아니라, 빠진 정보를 찾는 점검표입니다.

## 실습 2: 작업 지시서 작성

[작업 지시서 템플릿](../templates/task-brief.md)을 사용해 30~90분 작업 하나를 정의합니다.

좋지 않은 지시:

```text
내 논문을 잘 정리해 줘.
```

개선된 지시:

```text
sources/에 있는 세 논문의 초록만 읽고 연구 대상, 방법, 주요 결론을 표로 정리해 줘.
원문에 없는 주장은 추가하지 말고 각 항목에 파일명과 페이지를 표시해 줘.
완료 후 값이 비어 있거나 근거가 불분명한 셀을 따로 나열해 줘.
```

## 실습 3: 계획 먼저 검토하기

AI가 바로 파일을 바꾸게 하지 않고 다음 순서로 진행합니다.

1. 관련 파일과 현재 상태를 읽게 합니다.
2. 작업 계획과 변경 대상 파일을 제안하게 합니다.
3. 빠진 제약조건과 위험을 확인합니다.
4. 승인한 작은 단계만 실행합니다.
5. 변경사항을 직접 검토합니다.

### AI가 나에게 되묻게 하기 (양방향)

지시는 사람이 AI에게 내리는 한 방향만 있는 것이 아닙니다. **AI가 사람에게 질문하고, 검토를 요청하고, 다음 방향을 제안하게** 하면 초보자도 자기 생각을 더 분명히 정리할 수 있습니다. 막연할 때 특히 유용합니다.

**생각 인터뷰형** — 무엇을 원하는지 아직 흐릿할 때:

```text
바로 작업하지 말고, 제 목표를 분명히 하기 위해 저에게 한 번에 하나씩 질문해 주세요.
제 답을 듣고 다음 질문을 정하세요. 충분히 파악되면 그때 정리된 목표와 완료 조건을 제안해 주세요.
```

**검토·제안형** — 한 단계가 끝난 뒤:

```text
방금 결과를 스스로 검토해 주세요.
1. 잘된 점, 2. 미흡하거나 불확실한 점, 3. 제가 결정해야 할 선택지, 4. 추천하는 다음 한 단계.
제가 고르기 전에는 다음 작업을 진행하지 마세요.
```

핵심은 **결정권은 사람에게 남긴다는 것**입니다. AI는 질문·검토·제안까지 하고, 무엇을 할지는 참가자가 고릅니다.

## 실습 4: 검증 방법 선택

결과물 유형에 따라 최소 한 가지 이상의 외부 검증을 사용합니다.

| 결과물 | 검증 예시 |
|---|---|
| 연구 요약 | 원문 문장·페이지와 비교 |
| 인용 목록 | DOI, 저자, 연도, 실제 존재 여부 확인 |
| 지식 노트 | 원자료 링크와 핵심 주장 대조 |
| 프로그램 | 예시 입력, 오류 입력, 경계값 테스트 |
| 자동화 | 수작업 결과와 비교, 처리 전 파일 보관 |
| 설명서 | 다른 사람이 설명서만 보고 재현 |

## 실습 5: 결과를 보고 프롬프트 고치기 — 한 번에 한 줄만

첫 결과에서 아쉬운 점을 하나만 고르고, 그 실패를 막을 규칙 한 줄을 추가한 뒤 같은 검증 기준으로 다시 확인합니다. 프롬프트 전체를 매번 새로 쓰지 않습니다.

| 관찰한 실패 | 추가할 한 줄 규칙 예시 |
|---|---|
| 근거 없이 내용을 덧붙인다 | 제공한 자료에 없는 내용은 추정하지 말고 `확인 필요`로 표시한다. |
| 지정한 범위를 넘어 파일을 수정한다 | 지정한 폴더 밖의 파일은 수정하지 말고 먼저 질문한다. |
| 표 형식이 들쭉날쭉하다 | 열 이름과 출력 형식을 유지하고, 비어 있는 값은 `확인 필요`로 표시한다. |

반복되는 실수라면 다음 중 하나를 갱신합니다.

- 작업 지시서의 제약조건
- 완료 조건
- 검증 체크리스트
- 프로젝트의 `AGENTS.md`
- 입력 자료의 구조

한 번에 규칙 하나만 바꾸고, 바꾸기 전과 후의 결과를 같은 검증 기준으로 비교합니다. 그래야 그 규칙이 정말 효과가 있었는지 알 수 있습니다. 효과가 없으면 그 규칙은 지우거나 다시 씁니다.

> **이건 사실 더 큰 기술의 씨앗입니다.** "결과를 보며 지시문을 조금씩 고쳐 더 잘 작동하게 만드는 일"에는 이름이 있습니다. 관심이 있다면 [다음 단계](09-next-steps.md)에서 이 습관이 어디로 이어지는지 볼 수 있습니다. 지금은 몰라도 됩니다.

## 수업 종료 체크리스트

- [ ] 작업 지시서에 목표가 하나만 있다.
- [ ] AI가 읽어야 할 자료 범위가 명확하다.
- [ ] 금지 사항과 변경 가능 범위가 적혀 있다.
- [ ] 실행 전에 계획을 검토했다.
- [ ] AI가 만든 변경사항을 직접 확인했다.
- [ ] 결과를 확인한 외부 증거가 있다.
- [ ] 실패 또는 불확실한 항목을 숨기지 않고 기록했다.
- [ ] 관찰한 실패를 근거로 지시 또는 규칙 한 줄을 수정하고 다시 확인했다.
- [ ] 다음 작업에서 재사용할 규칙을 하나 추가했다.

## 숙제

같은 유형의 작업을 두 번 수행합니다.

1. 첫 번째 작업 지시서와 결과를 저장합니다.
2. 오류나 불편한 점을 찾습니다.
3. 관찰한 실패를 막는 한 줄 규칙을 지시서 또는 프로젝트 규칙에 추가합니다.
4. 두 번째 결과와 비교합니다.
5. [검증 기록](../templates/evidence-log.md)을 작성합니다.

## 제출물

- 최소 작업 프롬프트와 작업 지시서
- 수정 전후 비교
- 검증 기록
- 새로 추가한 작업 규칙 1개
- 주간 회고
