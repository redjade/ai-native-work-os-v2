# 그림으로 설명하기 — 내가 만드는 다이어그램

> **무엇을** 구조나 흐름을 그림 한 장으로 만들어 문서에 넣습니다.
> **왜** 글로 길게 설명해야 하는 것이 그림으로는 한눈에 보입니다.
> **나에게 무슨 의미** 남에게 설명하는 시간이 줄고, 내 머릿속 구조가 정리됩니다.

이 문서는 [쓸모 있는 프로젝트 찾기](12-find-your-project.md)의 가시화 갈래를 실제로 해 보는 방법입니다. 그림 편집 프로그램을 배우지 않아도 됩니다.

## 무엇을 그릴 가치가 있나

**그림이 이득인 것** — 글로 쓰면 길어지는 것들입니다.

- **구조**: 무엇이 무엇 안에 들어 있나 (폴더 구성, 문서 구성)
- **흐름**: 무엇이 무엇으로 이어지나 (작업 순서, 데이터 이동)
- **비교**: 두 가지가 어떻게 다른가 (전후, 옳은 예와 잘못된 예)
- **경계**: 안과 밖이 갈리는 곳 (보이는 것과 안 보이는 것, 되돌릴 수 없는 지점)

**그림이 필요 없는 것**

- 목록으로 충분한 것 (체크리스트, 준비물)
- 숫자를 비교하는 것 (이건 그림이 아니라 표나 차트)
- 한 번만 보고 넘길 것

한 번 그려서 여러 번 다시 볼 것만 만듭니다. 장식용 그림은 문서를 고칠 때 함께 낡습니다.

## SVG로 만드는 이유

이 과정에서는 그림을 `.svg` 형식으로 만듭니다.

- **글자로 된 파일**입니다. 그래서 AI에게 고쳐 달라고 할 수 있습니다.
- **커밋으로 변경이 남습니다.** 무엇을 어떻게 바꿨는지 diff에서 보입니다.
- 확대해도 흐려지지 않고, 파일이 작습니다.
- GitHub 문서에 그대로 보입니다.

즉 이 과정에서 배운 "챗 → 파일 → 커밋" 흐름이 그림에도 똑같이 적용됩니다.

## 만드는 순서

### 1. 종이나 말로 먼저 정리합니다

AI에게 시키기 전에 무엇을 그릴지 정합니다. 이 세 가지를 문장으로 씁니다.

```text
보여 줄 것:  (구조 / 흐름 / 비교 / 경계 중 하나)
상자 목록:   (5개 이내로)
가장 중요한 한 가지: (보는 사람이 이것만 기억한다면?)
```

상자가 8개를 넘으면 그림이 아니라 목록이 낫습니다. 나누어 두 장으로 만드세요.

### 2. AI에게 요청합니다

```text
아래 내용을 설명하는 SVG 다이어그램을 만들어 주세요.

보여 줄 것: [구조 / 흐름 / 비교 / 경계]
상자: [상자1 - 부제, 상자2 - 부제, ...]
가장 중요한 한 가지: [이것]

조건:
- 가로 720, 배경 흰색, 글꼴은 시스템 기본 글꼴로 지정
- 글자는 14px(제목)과 12px(부제) 두 가지만
- 색 의미: 파란색은 도구가 하는 일, 회색은 사라지거나 안 보이는 것,
  노란색은 사람이 판단하는 자리
- 상자 안의 글자가 상자를 넘지 않게 할 것
- 접근성을 위해 title과 desc를 넣을 것
파일로 저장하기 전에 먼저 내용을 보여 주세요.
```

### 3. 열어서 확인합니다

만든 `.svg` 파일을 브라우저로 열어 봅니다. 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 보입니다.

확인할 것:

- [ ] 글자가 상자 밖으로 넘치지 않는다.
- [ ] 상자와 글자가 겹치지 않는다.
- [ ] 화살표가 엉뚱한 곳을 가리키지 않는다.
- [ ] 잘린 부분 없이 전체가 보인다.
- [ ] 색을 못 봐도 글자만 읽어 이해된다.

한글은 생각보다 넓습니다. 14px에서 한 글자당 약 15px로 계산해 상자 너비에 들어오는지 봅니다. 부제가 길면 그림이 아니라 부제가 문제입니다. 줄이세요.

### 4. 고칩니다

넘치거나 겹치면 AI에게 그 부분만 말합니다.

```text
두 번째 상자의 부제가 상자를 넘칩니다. 부제를 더 짧게 하거나 상자를 넓혀 주세요.
```

### 5. 문서에 넣고 커밋합니다

문서에서 이렇게 불러옵니다. 대괄호 안에는 그림을 볼 수 없는 사람을 위한 설명을 씁니다.

```text
![세 단계가 순서대로 이어지고 마지막에 처음으로 돌아간다](assets/my-diagram.svg)
```

그리고 커밋합니다. 그림도 결과물이므로 [1주차에서 배운 흐름](02-session-1.md)을 그대로 씁니다.

## 흔한 실패

| 실패 | 이유 | 대응 |
|---|---|---|
| 글자가 상자를 넘침 | 부제가 너무 길다 | 5단어 이내로 줄인다 |
| 무슨 그림인지 모르겠다 | 상자가 너무 많다 | 8개 이하로, 아니면 두 장으로 나눈다 |
| 예쁘지만 정보가 없다 | 구조가 아니라 장식을 그렸다 | "이 그림 없이 설명하면 몇 문장 필요한가?"를 묻는다 |
| 어두운 화면에서 안 보인다 | 배경을 투명하게 두었다 | 배경을 흰색으로 고정한다 |
| 문서를 고쳤는데 그림이 옛날 내용 | 그림과 글이 갈라졌다 | 문서를 고칠 때 그림도 같이 본다 |

## 프로젝트로 만들 때

이걸 4주 프로젝트로 삼을 수도 있습니다. 가시화 갈래의 좋은 예입니다.

| 항목 | 내용 |
|---|---|
| "있으면 좋겠다" | 남에게 내 작업 방식을 설명할 때마다 매번 말로 그린다 |
| 결과물 | 내 작업 흐름·폴더 구조·의사결정 순서를 담은 그림 2~3장과 설명 페이지 |
| 위임 | "이 구조를 SVG로 그려 줘. 상자는 다섯 개 이내로" |
| 검증 | 그림만 보여 주고 상대가 설명 없이 이해하는지 확인 |
| 쓸모 | 다음에 설명할 때 이 그림을 열면 되면 성공 |

검증 방법이 특히 좋습니다. 사람에게 보여 주고 "이게 무슨 뜻으로 보이나요?"를 물으면 바로 드러납니다.

## 이 과정 문서의 그림

이 과정 문서에 쓰인 그림들도 같은 방식으로 만들었습니다. `docs/assets/` 폴더의 `.svg` 파일을 열어 보면 어떻게 만들었는지 그대로 보입니다. 참고하거나 복사해서 고쳐 쓰세요.
