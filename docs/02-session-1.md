# 1주차: 문제 정의, LLM Wiki와 Git 첫 결과물

## 이번 주 목표

모호한 아이디어를 4주 프로젝트로 줄이고, Obsidian에 작은 LLM Wiki를 만든 뒤 Git으로 변경 과정을 기록합니다. 수업 안에 다시 찾고 설명할 수 있는 첫 번째 지식 결과물을 완성합니다.

## 수업 전 준비

- [ ] [사전 준비 체크리스트](01-preflight.md)를 완료했다.
- [ ] 프로젝트 후보를 두 개 적었다.
- [ ] 공개하면 안 되는 자료를 구분했다.
- [ ] 개인 작업 폴더를 준비했다.
- [ ] Obsidian에서 수업용 볼트를 열 수 있다.
- [ ] GitHub 수업 저장소에 접근할 수 있다.

## 수업에서 배우는 것

- 문제와 해결책을 구분하는 법
- 산출물과 활동을 구분하는 법
- 완료 조건을 관찰 가능한 문장으로 쓰는 법
- 큰 프로젝트를 30~90분 작업으로 줄이는 법
- AI에게 파일을 보여 주기 전 확인할 사항
- LLM Wiki에서 출처, 주장, 해석과 질문을 구분하는 법
- 링크한 이유를 기록하고 필요한 정보를 다시 찾는 법
- Git으로 변경 전후를 확인하고 설명이 있는 저장 시점을 만드는 법

## 2시간 진행 순서

| 시간 | 활동 |
|---|---|
| 0~10분 | 계정·저장소·보안 상태 확인 |
| 10~30분 | LLM Wiki의 최소 구조와 좋은 노트 기준 |
| 30~50분 | Obsidian 작성부터 Git 커밋·푸시까지 시연 |
| 50~105분 | 개인 Wiki와 첫 결과물 제작 |
| 105~115분 | 서로의 인덱스만 보고 정보 찾기 |
| 115~120분 | 변경 확인, 커밋, 회고와 다음 행동 확정 |

## 실습 1: 프로젝트 한 문장

다음 형식으로 작성합니다.

```text
[사용자]가 [상황]에서 겪는 [구체적인 문제]를 줄이기 위해
[형식이 분명한 결과물]을 만든다.
```

예시:

```text
논문 초안을 준비하는 대학원생이 출처와 주장을 혼동하는 문제를 줄이기 위해
출처 15개의 핵심 주장과 인용 위치를 확인할 수 있는 근거표를 만든다.
```

## 실습 2: 완료 조건

“좋다”, “유용하다”, “잘 된다” 대신 관찰 가능한 조건을 사용합니다.

- [ ] 결과물의 파일 또는 링크가 존재한다.
- [ ] 예시 입력으로 실행하거나 읽어 볼 수 있다.
- [ ] 예상 결과와 실제 결과를 비교할 수 있다.
- [ ] 다른 사람이 설명서를 보고 핵심 기능을 확인할 수 있다.
- [ ] 민감정보가 포함되지 않는다.

## 실습 3: LLM Wiki 작업공간

[프로젝트 정의서](../templates/project-brief.md)를 복사해 `PROJECT.md`로 저장합니다.

최소 구조:

```text
project-name/
  HOME.md
  PROJECT.md
  TASKS.md
  LOG.md
  README.md
  knowledge/
    index.md
    sources/
    concepts/
    questions/
  outputs/
  logs/
```

처음부터 복잡한 분류법을 만들지 않습니다. 각 폴더의 역할은 다음과 같습니다.

- `HOME.md`: 현재 프로젝트와 다음 행동을 보여 주는 시작 화면
- `knowledge/index.md`: 주제의 전체 지도와 중요한 노트 링크
- `sources/`: 원문, 책, 논문, 웹페이지 등 출처 중심 노트
- `concepts/`: 여러 출처를 비교해 이해한 개념 노트
- `questions/`: 아직 확인하지 못한 질문과 불확실성
- `outputs/`: 다른 사람이 읽거나 사용할 결과물
- `logs/`: 작업 과정과 회고

### 좋은 지식 노트의 최소 항목

[지식 노트 템플릿](../templates/knowledge-note.md)을 사용합니다.

```text
출처:
핵심 주장:
내 해석:
다음에 사용할 곳:
```

LLM이 만든 요약문을 대량으로 저장하지 않습니다. 원출처와 AI의 해석을 구분하고, 실제 프로젝트에서 다시 사용할 노트만 남깁니다.

### 링크 기준

링크 수는 점수가 아닙니다. 다음 중 하나를 설명할 수 있을 때 링크합니다.

- 같은 주장을 지지하거나 반박한다.
- 상위 개념과 세부 사례의 관계다.
- 현재 질문을 해결할 근거다.
- 앞으로 만들 결과물에서 함께 사용한다.

링크 옆에는 가능하면 관계를 한 문장으로 적습니다.

## 실습 4: LLM과 함께 노트 만들기

AI에는 다음과 같이 요청합니다.

```text
이 자료에서 원문이 직접 말하는 핵심 주장과 내가 추가로 해석해야 하는 부분을 구분해 주세요.
각 주장에 출처 위치를 표시하고, 근거가 없는 내용은 추가하지 마세요.
아직 노트 파일은 수정하지 말고 먼저 표로 보여 주세요.
```

AI의 답을 그대로 저장하지 않고 다음을 확인합니다.

- [ ] 원출처가 실제로 존재한다.
- [ ] 주장과 출처 위치가 일치한다.
- [ ] 사실, AI의 요약과 내 해석이 구분된다.
- [ ] 모르는 내용은 질문으로 남겼다.
- [ ] 이 노트를 사용할 프로젝트 위치가 적혀 있다.

## 실습 5: Git 작업 루프

이번 주에는 다음 흐름만 사용합니다.

```text
pull → 작업 → status → diff → add → commit → push
```

각 단계의 의미:

- `pull`: GitHub의 최신 변경을 가져온다.
- `status`: 어떤 파일이 달라졌는지 확인한다.
- `diff`: 파일 안에서 정확히 무엇이 달라졌는지 확인한다.
- `add`: 이번 저장 시점에 포함할 변경을 선택한다.
- `commit`: 변경 이유가 적힌 저장 시점을 만든다.
- `push`: 로컬 저장 시점을 GitHub에 전달한다.

터미널 예시:

```bash
git pull
git status
git diff
git add HOME.md PROJECT.md knowledge/
git commit -m "docs: add initial knowledge map"
git push
```

앱이나 GitHub Desktop을 사용해도 됩니다. 중요한 것은 명령을 외우는 것이 아니라 커밋 전에 `status`와 `diff`로 변경 내용을 직접 확인하는 것입니다.

이번 주에는 브랜치, rebase와 복잡한 충돌 해결을 다루지 않습니다.

## 실습 6: 첫 번째 작은 결과물

첫 결과물은 30분 안에 만들어야 합니다.

예시:

- 연구: 출처 3개의 비교표
- 지식관리: 출처 노트 2개, 개념 노트 1개와 인덱스 1개
- 제작: 고정된 예시 입력 하나를 처리하는 화면 또는 스크립트

완성도가 낮아도 열어 보거나 실행할 수 있어야 합니다.

## 수업 종료 체크리스트

- [ ] 프로젝트 문제를 한 문장으로 설명할 수 있다.
- [ ] 4주 최종 결과물의 형태가 정해졌다.
- [ ] 하지 않을 일이 적혀 있다.
- [ ] 완료 조건이 세 개 이상 있다.
- [ ] `knowledge/index.md`에서 중요한 노트를 찾을 수 있다.
- [ ] 출처와 내 해석이 구분된 지식 노트가 있다.
- [ ] 각 링크의 관계를 설명할 수 있다.
- [ ] 첫 번째 작은 결과물이 존재한다.
- [ ] 결과물의 한계나 오류를 하나 이상 기록했다.
- [ ] `git status`와 `git diff` 또는 같은 기능의 화면을 확인했다.
- [ ] 설명이 있는 커밋을 만들고 GitHub에 푸시했다.
- [ ] 다음 작업 하나가 정해졌다.

## 숙제

1. 인덱스 노트 1개를 완성합니다.
2. 출처 노트 3개와 개념 노트 2개를 만듭니다.
3. 이유를 설명할 수 있는 링크를 3개 이상 연결합니다.
4. 작업 과정을 설명 가능한 단위로 나누어 두 번 이상 커밋해 봅니다. 커밋 수 자체는 평가하지 않습니다.
5. 첫 결과물을 한 번 개선합니다.
6. AI 사용 전과 사용 후에 걸린 시간을 기록합니다.
7. [주간 회고](../templates/weekly-review.md)를 작성합니다.
8. 다음 질문에 한 문장씩 답합니다.

```text
무엇을 만들었는가?
무엇을 배웠는가?
무엇을 기록했는가?
다음에는 무엇을 개선할 것인가?
```
