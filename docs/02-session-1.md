# 1주차: 문제 정의, LLM Wiki와 Git 첫 결과물

## 이번 주 목표

모호한 아이디어를 4주 프로젝트로 줄이고, Obsidian에 작은 LLM Wiki를 만든 뒤 Git으로 변경 과정을 기록합니다. 수업 안에 다시 찾고 설명할 수 있는 첫 번째 지식 결과물을 완성합니다.

## LLM Wiki란 무엇인가

> **무엇을** LLM과 함께 만들되, 사람이 검증해서 남기는 개인 지식 노트 모음입니다.
> **왜** AI의 답은 편하지만 흩어지고 틀릴 수 있습니다. 확인한 것만 골라 다시 찾을 수 있게 남기기 위해서입니다.
> **나에게 무슨 의미** "AI가 말해 준 것"과 "내가 확인한 것"을 구분하는 습관이 생기고, 그 결과가 자산으로 쌓입니다.

**유래와 의도.** 위키(wiki)는 원래 여러 사람이 함께 고쳐 나가는 연결된 문서 모음입니다. 여기에 "LLM"을 붙인 이유는, 이제 그 공동 저자 중 하나가 AI라는 점을 분명히 하기 위해서입니다. 다만 AI는 자신 있게 틀리기도 하므로, LLM Wiki의 규칙은 단순합니다 — **원문(출처)과 AI의 해석과 내 판단을 섞지 않는다.** 요약을 잔뜩 모으는 곳이 아니라, 확인을 거쳐 다시 쓸 것만 남기는 곳입니다.

이 과정에서 LLM Wiki는 화려한 지식관리 시스템을 만드는 것이 목표가 아닙니다. **작게 시작해서, 눈에 보이고, 안전하게 남는** 첫 지식 결과물을 만드는 것이 목표입니다.

- 문제와 해결책을 구분하는 법
- 산출물과 활동을 구분하는 법
- 완료 조건을 관찰 가능한 문장으로 쓰는 법
- 큰 프로젝트를 30~90분 작업으로 줄이는 법
- AI에게 파일을 보여 주기 전 확인할 사항
- LLM Wiki에서 출처, 주장, 해석과 질문을 구분하는 법
- 링크한 이유를 기록하고 필요한 정보를 다시 찾는 법
- Git으로 변경 전후를 확인하고 설명이 있는 저장 시점을 만드는 법

## 실습 1: 프로젝트 한 문장

다음 형식으로 작성합니다.

```text
[사용자]가 [상황]에서 겪는 [구체적인 문제]를 줄이기 위해

```

```text

출처 15개의 핵심 주장과 인용 위치를 확인할 수 있는 근거표를 만든다.
```

## 실습 3: LLM Wiki 작업공간

### 잠깐 — 템플릿이란?

이 과정에서 자주 나오는 **템플릿**은 빈칸이 있는 견본 파일입니다. 매번 백지에서 시작하지 않도록, 무엇을 적어야 하는지 미리 칸을 만들어 둔 것입니다.

- 사용법: `templates/` 폴더의 견본을 **복사**한 뒤, 내 프로젝트 폴더에서 빈칸을 채웁니다.
- 원본은 그대로 두고 복사본을 고칩니다.
- 칸이 안 맞으면 지우거나 바꿔도 됩니다. 템플릿은 규칙이 아니라 출발점입니다.

각 템플릿 파일 맨 위에는 "무엇을 · 왜 · 언제 쓰나"가 한 줄로 적혀 있으니, 처음 쓸 때 그 줄을 먼저 읽습니다.

### 작업공간 만들기

[프로젝트 정의서](../templates/project-brief.md)를 복사해 `PROJECT.md`로 저장합니다.

최소 구조:

```text
project-name/
  HOME.md
  PROJECT.md
  TASKS.md
  LOG.md
  README.md
  knowledge/
    index.md
    sources/
    concepts/
    questions/
  outputs/
  logs/
```

처음부터 복잡한 분류법을 만들지 않습니다. 각 폴더의 역할은 다음과 같습니다.

- `HOME.md`: 현재 프로젝트와 다음 행동을 보여 주는 시작 화면
- `knowledge/index.md`: 주제의 전체 지도와 중요한 노트 링크
- `sources/`: 원문, 책, 논문, 웹페이지 등 출처 중심 노트
- `concepts/`: 여러 출처를 비교해 이해한 개념 노트
- `questions/`: 아직 확인하지 못한 질문과 불확실성
- `outputs/`: 다른 사람이 읽거나 사용할 결과물
- `logs/`: 작업 과정과 회고

### 지금 어디에서 작업하나 — 경로 감각

AI에게 파일을 맡길 때 가장 흔한 사고는 **엉뚱한 폴더의 파일을 고치는 것**입니다. 그래서 명령을 외우기 전에, 지금 내가 어느 폴더에 있고 이 파일이 어디에 있는지를 **읽는 감각**이 먼저입니다.

경로는 폴더가 이어진 주소입니다. 프로젝트 폴더가 기준점이고, 그 안에서의 위치가 경로입니다.

- 예: `knowledge/sources/2021-kim.md` → "프로젝트 폴더 안 → knowledge 안 → sources 안 → 그 파일"

**화면으로 경로 읽기 (권장).** 같은 파일 하나를 세 곳에서 찾아보고 위치가 같은지 확인합니다.

1. **파일 탐색기**(Finder / Windows 탐색기): 폴더를 열어 계층을 눈으로 봅니다.
2. **Obsidian 왼쪽 파일 트리**: 볼트 안에서 그 노트의 위치.
3. **GitHub Desktop 또는 GitHub 웹**: 바뀐 파일이 저장소 어디에 있는지 상대경로로 표시됩니다.

세 화면에서 같은 파일의 경로가 같게 보이면 경로 감각이 잡힌 것입니다.

**AI에게 위치를 확인시키기.** 작업 전 이렇게 물으면 엉뚱한 폴더 사고를 줄입니다.

```text
지금 작업 폴더가 어디인지, 수정할 파일의 경로가 정확히 무엇인지 먼저 알려 주세요.
아직 고치지 말고, 제가 확인한 뒤 진행하겠습니다.
```

**심화 (선택) — 내가 어디 있는지 3개 명령으로 보기.** GitHub Desktop은 *바뀐 파일의 위치*는 보여 주지만, *지금 내가 서 있는 폴더*라는 감각까지 대신하지는 않습니다. 그 감각을 직접 느끼고 싶다면 터미널에서 이 세 가지만 써 봅니다. Git이 아니라 "위치 보기"용입니다.

```bash
pwd            # 지금 내가 있는 폴더의 전체 경로
ls             # 이 폴더 안에 무엇이 있는지 목록
cd knowledge   # knowledge 폴더로 이동 (cd ..는 한 단계 위로)
```

이 세 명령은 외울 필요 없습니다. "어디에 있지?"가 궁금할 때 열어 보는 창이라고 생각하면 됩니다.

### 좋은 지식 노트의 최소 항목

[지식 노트 템플릿](../templates/knowledge-note.md)을 사용합니다.

```text
출처:
핵심 주장:
내 해석:
다음에 사용할 곳:
```

LLM이 만든 요약문을 대량으로 저장하지 않습니다. 원출처와 AI의 해석을 구분하고, 실제 프로젝트에서 다시 사용할 노트만 남깁니다.

### 링크 기준

링크 수는 점수가 아닙니다. 다음 중 하나를 설명할 수 있을 때 링크합니다.

- 같은 주장을 지지하거나 반박한다.
- 상위 개념과 세부 사례의 관계다.
- 현재 질문을 해결할 근거다.
- 앞으로 만들 결과물에서 함께 사용한다.

링크 옆에는 가능하면 관계를 한 문장으로 적습니다.

## 실습 4: LLM과 함께 노트 만들기

AI에는 다음과 같이 요청합니다.

```text
이 자료에서 원문이 직접 말하는 핵심 주장과 내가 추가로 해석해야 하는 부분을 구분해 주세요.
각 주장에 출처 위치를 표시하고, 근거가 없는 내용은 추가하지 마세요.
아직 노트 파일은 수정하지 말고 먼저 표로 보여 주세요.
```

AI의 답을 그대로 저장하지 않고 다음을 확인합니다.

- [ ] 원출처가 실제로 존재한다.
- [ ] 주장과 출처 위치가 일치한다.
- [ ] 사실, AI의 요약과 내 해석이 구분된다.
- [ ] 모르는 내용은 질문으로 남겼다.
- [ ] 이 노트를 사용할 프로젝트 위치가 적혀 있다.

## 실습 5: 챗에서 파일로 옮기기 (챗 → 산출물)

챗(ChatGPT·Claude 대화)에서 좋은 결과가 나왔다면, **그대로 두면 사라집니다.** 이번 실습에서 그것을 파일로 옮깁니다. 이 과정의 핵심 다리입니다.

절차:

1. 실습 4에서 확인한 표·정리 내용을 고릅니다. (AI가 준 것 전부가 아니라, **내가 검증한 부분만**)
2. 해당 노트 파일(`knowledge/sources/...` 또는 `concepts/...`)에 붙여 넣습니다.
3. "출처 / 핵심 주장 / 내 해석"을 구분해 정리합니다. 채팅 말투는 지웁니다.
4. 어디서 온 내용인지(원문, AI 해석, 내 판단) 표시가 남아 있는지 확인합니다.

확인:

- [ ] 노트를 열면 챗 없이도 내용이 이해된다.
- [ ] AI가 준 것 중 검증한 것만 남겼다.
- [ ] 원문·AI 해석·내 판단이 섞여 있지 않다.

이렇게 파일로 옮긴 뒤에야 다음 실습(Git)에서 "안전하게 남는" 상태가 됩니다.

## 실습 6: Git으로 안전하게 남기기

> **무엇을** 방금 만든 파일들을 되돌릴 수 있는 저장 시점으로 남기고 GitHub에 올립니다.
> **왜** 변경을 기록해 두면 잘못돼도 돌아갈 수 있고, GitHub에서 결과물이 눈에 보입니다.
> **나에게 무슨 의미** 작업이 사라지지 않고, 남에게 보여 줄 수 있는 안전한 상태가 됩니다.

이번 주 흐름은 하나입니다.

```text
변경 확인 → 저장 시점 만들기(커밋) → GitHub에 올리기(푸시)
```

용어(외울 필요 없이 뜻만):

- **커밋(commit)**: 변경 이유가 적힌 저장 시점. 게임의 세이브 지점과 비슷합니다.
- **푸시(push)**: 그 저장 시점을 GitHub에 올려 백업·공유하는 것.
- **diff**: 무엇이 어떻게 달라졌는지 보여 주는 화면.

### 기본 경로 — 화면(GUI)으로 하기

터미널이 익숙하지 않아도 됩니다. **처음에는 눈으로 보며 하는 것을 권장합니다.**

- **GitHub Desktop** 또는 사용하는 **에이전트 앱(Codex 앱 등)의 Git 화면**을 엽니다.
- 다음 순서로 진행합니다.
  1. **변경된 파일 목록**을 봅니다. (내가 만든 파일들이 맞는지 확인)
  2. 각 파일을 눌러 **diff(바뀐 내용)**를 눈으로 확인합니다.
  3. 커밋 메시지에 **무엇을 왜 바꿨는지** 한 줄 적습니다. 예: `add initial knowledge map`
  4. **Commit**을 누릅니다. (저장 시점 생성)
  5. **Push**를 눌러 GitHub에 올립니다.
- GitHub 웹페이지를 새로고침하면 방금 올린 파일이 보입니다. **이 "보인다"는 확인이 중요합니다.**

가장 중요한 것은 버튼 순서가 아니라, **커밋하기 전에 diff로 바뀐 내용을 직접 눈으로 확인**하는 습관입니다.

### 심화 (선택) — 터미널로 하기

터미널이 편해지고 싶다면 같은 일을 명령으로 할 수 있습니다. 지금 당장 할 필요는 없습니다.

```bash
git pull      # GitHub의 최신 변경을 가져온다
git status    # 어떤 파일이 달라졌는지 확인한다
git diff      # 파일 안에서 무엇이 달라졌는지 확인한다
git add HOME.md PROJECT.md knowledge/   # 저장에 포함할 변경 선택
git commit -m "docs: add initial knowledge map"   # 저장 시점 생성
git push      # GitHub에 올리기
```

화면으로 하든 터미널로 하든 결과는 같습니다. 이번 주에는 브랜치, rebase와 복잡한 충돌 해결을 다루지 않습니다.

## 실습 7: 첫 번째 작은 결과물

첫 결과물은 30분 안에 만들어야 합니다.

예시:

- 연구: 출처 3개의 비교표
- 지식관리: 출처 노트 2개, 개념 노트 1개와 인덱스 1개
- 제작: 고정된 예시 입력 하나를 처리하는 화면 또는 스크립트

완성도가 낮아도 열어 보거나 실행할 수 있어야 합니다.

## 수업 종료 체크리스트

- [ ] 프로젝트 문제를 한 문장으로 설명할 수 있다.
- [ ] 4주 최종 결과물의 형태가 정해졌다.
- [ ] 하지 않을 일이 적혀 있다.
- [ ] 완료 조건이 세 개 이상 있다.
- [ ] `knowledge/index.md`에서 중요한 노트를 찾을 수 있다.
- [ ] 출처와 내 해석이 구분된 지식 노트가 있다.
- [ ] 각 링크의 관계를 설명할 수 있다.
- [ ] 첫 번째 작은 결과물이 존재한다.
- [ ] 결과물의 한계나 오류를 하나 이상 기록했다.
- [ ] `git status`와 `git diff` 또는 같은 기능의 화면을 확인했다.
- [ ] 설명이 있는 커밋을 만들고 GitHub에 푸시했다.
- [ ] 다음 작업 하나가 정해졌다.

## 숙제
