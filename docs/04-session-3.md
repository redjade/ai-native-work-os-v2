# 3주차: 기록과 재사용

## 이번 주 목표

채팅 기록에 의존하지 않고, 다른 사람과 다음 주의 내가 이해할 수 있는 프로젝트 운영체계를 만듭니다.

## 도구의 역할

- Obsidian: 사람이 읽고 연결하는 작업공간
- Git: 무엇이 언제 바뀌었는지 기록하고 복구하는 장치
- GitHub: 저장소를 백업하거나 선택적으로 공유하는 장소
- AI 에이전트: 허용된 자료와 규칙 안에서 작업하는 실행자
- `PROJECT.md`: 프로젝트 목표와 완료 조건
- `AGENTS.md`: 에이전트가 반복해서 따라야 할 작업 규칙
- `README.md`: 처음 보는 사람을 위한 사용 설명

## 권장 작업공간

```text
HOME.md
AGENTS.md
SECURITY.md
projects/
  project-name/
    PROJECT.md
    TASKS.md
    DECISIONS.md
    LOG.md
    README.md
    output/
knowledge/
templates/
```

모든 프로젝트가 이 구조를 그대로 쓸 필요는 없습니다. 각 파일의 역할이 겹치지 않도록 하는 것이 더 중요합니다.

## 실습 1: 대시보드 만들기

### 왜 대시보드인가

프로젝트가 하나뿐이고 매일 붙어 있다면 대시보드는 없어도 됩니다. 하지만 **여러 일을 동시에 굴리거나, 며칠 만에 다시 프로젝트로 돌아오면** "지금 어디까지 했더라"를 매번 다시 떠올려야 합니다. 대시보드는 그 **재구성 비용**을 없앱니다.

- 회사에서 여러 업무를 관리해 본 사람에게는 익숙한 감각입니다. 상태를 **압축해 한 화면에 두고, 주기적으로 같은 자리에서** 확인합니다.
- 자세한 내용을 담는 곳이 아닙니다. **판단에 필요한 최소 정보 — 지금 상태와 다음 행동 — 만** 둡니다.
- 매주 돌아올 때 이 화면부터 보면, 채팅이나 파일을 뒤지지 않고도 바로 이어서 일할 수 있습니다.

즉 대시보드는 "보기 좋으라고" 만드는 것이 아니라, **미래의 나(그리고 함께 보는 사람)가 맥락을 다시 쌓지 않게** 하려고 만듭니다.

### 만들기

[대시보드 템플릿](../templates/dashboard.md)을 `HOME.md`로 복사합니다.

대시보드에는 다음 항목만 둡니다.

- 현재 프로젝트
- 이번 주 결과물
- 상태
- 근거 링크
- 가장 큰 위험
- 다음 행동 하나
- 마지막 검토일

## 실습 2: 판단 기록하기

`DECISIONS.md`에는 중요한 선택만 기록합니다.

```text
날짜:
결정:
선택한 이유:
고려한 대안:
다시 검토할 조건:
```

도구를 선택한 이유, 공개 범위, 데이터 구조 변경처럼 나중에 되돌아볼 가치가 있는 판단을 기록합니다.

## 실습 3: AGENTS.md 만들기

> **무엇을** AI 에이전트가 이 프로젝트에서 반복해서 지켜야 할 규칙을 적어 두는 파일입니다.
> **왜** 매번 같은 주의사항을 대화로 반복하지 않기 위해서입니다. 한 번 적어 두면 도구가 계속 참고합니다.
> **나에게 무슨 의미** "이 폴더만 고쳐", "출처를 지어내지 마"처럼 자주 하는 말을 규칙으로 고정할 수 있습니다.

**유래.** 사람이 읽는 사용 설명서가 `README.md`라면, `AGENTS.md`는 **AI 에이전트가 읽는 작업 지침서**입니다. 여러 코딩 에이전트 도구들이 프로젝트 폴더에서 이 파일을 자동으로 찾아 규칙으로 참고하도록 관례가 자리 잡으면서, 도구에 상관없이 쓸 수 있는 공통 지침 파일이 되었습니다. 도구마다 이름이 다를 수 있지만(예: 도구 전용 지침 파일), 생각은 같습니다 — **지속적으로 지켜야 할 규칙을 한곳에 둔다.**

**비유로 기억하기.** 에이전트는 작업을 시작할 때마다 그 환경에 **처음 도착**합니다. 냉동수면에서 막 깨어난 사람이 눈앞의 안내문을 읽고 "여기가 어디고 무엇을 해야 하나"를 파악하듯, 에이전트는 `AGENTS.md`를 읽고 상황을 파악합니다. 그래서 이 파일은 "이미 알고 있겠지" 하는 전제 없이, **처음 온 사람에게 설명하듯 구체적으로** 적어야 합니다. 추상적인 다짐("항상 잘한다")이 아니라, 처음 도착한 이가 바로 따를 수 있는 구체적인 지시가 좋은 규칙인 이유입니다.

핵심 규칙의 원본은 한곳에만 둡니다. 도구 전용 지침 파일이 따로 필요해도 같은 내용을 중복해서 쓰지 않고 `AGENTS.md`를 참조하게 합니다.

[AGENTS.md 템플릿](../templates/AGENTS.template.md)을 참고합니다.

좋은 규칙:

- 수정 가능한 폴더가 명확하다.
- 실행·검증 방법이 실제 명령이나 절차로 적혀 있다.
- 민감정보와 금지 행동이 명확하다.
- 완료 시 확인할 항목이 있다.

좋지 않은 규칙:

- “항상 최고 품질로 작성한다.”
- “절대 실수하지 않는다.”
- 현재 작업에만 적용되는 긴 요구사항
- 실행할 수 없거나 확인할 수 없는 기준

## 실습 4: Git으로 작은 변경 기록하기

한 커밋에는 한 가지 설명 가능한 변화만 담습니다.

커밋 메시지 예시:

```text
docs: add source verification checklist
feat: generate comparison table from three sample files
fix: handle empty input without deleting output
```

커밋 수 자체는 점수가 아닙니다. 무엇이 바뀌었는지 설명하고 필요한 경우 이전 상태로 돌아갈 수 있어야 합니다.

## 실습 5: 재현성 시험

동료가 다음 정보만 보고 결과물을 확인합니다.

- README
- 예시 입력
- 실행 또는 사용 절차
- 예상 결과

설명한 사람이 옆에서 추가로 말해야 했다면 그 내용을 README에 보충합니다.

## 수업 종료 체크리스트

- [ ] `HOME.md`에서 현재 상태를 확인할 수 있다.
- [ ] 프로젝트 목표와 현재 작업이 분리되어 있다.
- [ ] 중요한 선택의 이유가 기록되어 있다.
- [ ] `AGENTS.md`에 실제로 실행 가능한 규칙이 있다.
- [ ] 변경사항이 설명 가능한 단위로 기록되어 있다.
- [ ] README만 보고 핵심 결과를 확인할 수 있다.
- [ ] 기록할 필요가 없는 채팅과 남겨야 할 지식을 구분했다.

## 숙제

1. 가족이나 동료 한 명에게 README만 전달합니다.
2. 설명 없이 결과물을 열거나 실행해 달라고 요청합니다.
3. 막힌 지점과 질문을 기록합니다.
4. README와 작업 규칙을 수정합니다.
5. 수정 전후 차이를 커밋 또는 로그로 남깁니다.
