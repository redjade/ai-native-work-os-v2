# 과정 안내와 프로젝트 선택

## 과정의 목표

이 과정에서는 AI를 답변 도구가 아니라 **작업을 위임하고 검토하는 협업자**로 사용합니다. 참가자가 도구에 의존하지 않고 작업을 통제하려면 다음 질문에 답할 수 있어야 합니다.

1. 지금 해결하려는 문제는 무엇인가?
2. 이번 주에 확인할 수 있는 결과물은 무엇인가?
3. AI에게 어떤 자료와 권한을 줄 것인가?
4. 결과가 맞는지 어떻게 확인할 것인가?
5. 다음에 다시 사용할 수 있도록 무엇을 기록할 것인가?

## 이 과정이 지키는 약속

이 과정에서 얻는 가장 중요한 경험은 특정 도구를 잘 다루게 되는 것이 아닙니다. **AI와의 대화에서 만든 결과물이 사라지지 않고, 눈에 보이며, 안전하게 남는** 작업 방식입니다.

- **보인다**: 결과물이 채팅 기록 속이 아니라 파일과 GitHub에서 눈에 보입니다.
- **남는다**: 변경이 Git으로 기록되어 되돌리거나 이어서 작업할 수 있습니다.
- **이어진다**: 챗에서 편하게 시작하되, 그 결과를 파일로 옮겨 커밋하는 흐름을 익힙니다.

챗(ChatGPT·Claude 대화)은 편하고 빠릅니다. 하지만 대화는 흩어지고 사라집니다. 그래서 이 과정은 **"챗 → 파일 → 커밋 → GitHub에서 보임"** 이라는 다리를 반복해서 연습합니다. 이 다리를 건너는 습관이 이 과정의 핵심 기술입니다.

## 완성도보다 쓸모

이 과정에서 만드는 결과물은 상품처럼 매끈할 필요가 **없습니다.** 소프트웨어로서 완성도가 낮아도, **나나 다른 한 사람에게 실제로 쓸모가 있으면 그것으로 성공**입니다. 이것이 이 과정이 가장 강조하는 지점입니다.

- 거친 웹페이지라도 매번 찾아 헤매던 정보를 한곳에 모아 주면 성공입니다.
- 투박한 시각화라도 안 보이던 패턴을 보여 주면 성공입니다.
- 버튼 하나짜리 도구라도 반복하던 일을 줄여 주면 성공입니다.

AI에게 많은 부분을 맡겨 빠르게 만들되(요즘 이런 방식을 **바이브 코딩(vibe coding)**, 넓게는 **에이전틱 엔지니어링**이라고 부릅니다), 사람은 "이게 실제로 쓸모 있나"를 판단하고 검증합니다. 기준은 매끄러움이 아니라 쓸모입니다.

논문·연구가 아니어도 됩니다. 유튜브 기획, 관심 주제 분석, 자주 쓰는 정보 모음처럼 **내가 평소에 "이런 거 있으면 좋겠다" 싶던 것**을 고르는 방법은 [쓸모 있는 프로젝트 찾기](12-find-your-project.md)를 참고합니다.

## 산출물 루프

모든 프로젝트는 같은 여섯 단계를 반복합니다.

### 1. 정의

- 사용자와 문제를 한 문장으로 적습니다.
- 이번 작업의 결과물 형식을 정합니다.
- 완료 조건과 하지 않을 일을 적습니다.

### 2. 위임

- AI에 목표, 맥락, 제약조건, 완료 조건을 전달합니다.
- 큰 작업은 검토 가능한 작은 단계로 나눕니다.
- 실행 전 계획을 먼저 확인합니다.

### 3. 검증

- 출처, 테스트, 예시 입력, 직접 비교로 확인합니다.
- AI의 설명이 아니라 외부 증거를 남깁니다.
- 틀린 결과를 발견하면 작업 지시나 규칙을 수정합니다.

### 4. 기록

- 무엇을 바꾸었는지 Git과 작업 로그에 남깁니다.
- 중요한 선택과 그 이유를 기록합니다.
- 반복되는 실수는 체크리스트나 `AGENTS.md` 규칙으로 바꿉니다.

### 5. 공유

- 다른 사람이 이해할 수 있도록 README를 작성합니다.
- 공개 전 개인정보, 비밀정보, 출처, 라이선스를 확인합니다.
- 공개가 부적절한 프로젝트는 수업 안에서만 시연합니다.

### 6. 개선

- 효과가 있었던 방법과 없었던 방법을 구분합니다.
- 다음 주에 바꿀 행동을 하나만 정합니다.
- 템플릿과 작업 규칙을 실제 경험에 맞게 갱신합니다.

## 프로젝트 선정 기준

다음 항목에 모두 답할 수 있는 프로젝트를 선택합니다.

- [ ] 내가 실제로 겪는 문제인가?
- [ ] 결과물을 파일, 링크, 표, 문서 또는 실행 화면으로 보여 줄 수 있는가?
- [ ] 4주 안에 작은 완성본을 만들 수 있는가?
- [ ] 1주 안에 첫 번째 축소판을 만들 수 있는가?
- [ ] 정확성을 확인할 방법이 있는가?
- [ ] 민감정보 없이 진행할 수 있는가?
- [ ] 실패해도 배울 수 있는가?

## 좋은 범위와 나쁜 범위

| 너무 큰 표현 | 4주 프로젝트로 줄인 표현 |
|---|---|
| 논문을 AI로 쓴다 | 주제 관련 출처 15개를 분류하고 주장-근거표를 만든다 |
| 개인 지식관리 시스템을 완성한다 | 한 주제의 노트 20개를 같은 규칙으로 작성하고 다시 찾는 실험을 한다 |
| 앱을 만든다 | 한 가지 입력을 받아 한 가지 결과를 보여 주는 도구를 만든다 |
| 공부를 자동화한다 | 오답 기록에서 다음 복습 문제 5개를 만드는 흐름을 만든다 |

자기 상황에 가까운 예시가 필요하면 [대상별 프로젝트 예시](11-examples-by-segment.md)를 참고합니다. 여러 자료(논문·기사·리포트)를 다루는 프로젝트라면 [워크드 예시: 여러 논문 정리](10-worked-example-papers.md)가 전체 과정을 단계별로 보여 줍니다.

## 프로젝트 트랙

### 연구 트랙

최종 결과물 예시:

- 연구 질문과 범위
- 출처 및 서지정보 표
- 주장-근거 연결표
- 목차 또는 검토 가능한 초안
- 사람이 확인한 인용 검증 기록

### 지식관리 트랙

최종 결과물 예시:

- Obsidian 볼트 구조
- 노트 작성 규칙과 템플릿
- 주제 지도 또는 인덱스
- 검색·회수 테스트 결과
- 주간 검토 대시보드

### 제작 트랙

최종 결과물 예시:

- 실행 가능한 작은 프로그램 또는 자동화
- 예시 입력과 예상 출력
- 실행 방법
- 테스트 또는 검증 기록
- 안전한 공개본

## 수업의 반복 구조

매주 같은 리듬을 사용합니다.

| 시간 | 활동 |
|---|---|
| 0~10분 | 지난 결과물과 막힌 지점 확인 |
| 10~30분 | 이번 주 핵심 개념 |
| 30~50분 | 강사 시연 |
| 50~100분 | 개인 프로젝트 제작 |
| 100~112분 | 동료 검토와 설명 |
| 112~120분 | 기록, 커밋, 다음 행동 확정 |

## 수료 기준

출석만으로 수료하지 않습니다. 다음 항목을 확인합니다.

- [ ] 최종 결과물을 열거나 실행할 수 있다.
- [ ] 프로젝트의 문제와 사용자를 설명할 수 있다.
- [ ] 완료 조건을 충족했다는 근거가 있다.
- [ ] AI가 만든 결과를 검증한 기록이 있다.
- [ ] 다른 사람이 따라 할 README가 있다.
- [ ] 공개 또는 시연 전에 보안 점검을 통과했다.
- [ ] 다음 30일 개선 계획이 있다.
